# トークン効率ルール

## 調査と指示の読み込み

- 最小の読み取り専用確認から始めます。関連Issueの目的・受入条件、現在のコミット、最新差分、未対応指摘に対象を絞り、証拠が必要な場合だけ調査範囲を広げます。
- 過去レビューや履歴を毎回全文取得しません。ファイル名・該当行・必要なJSON項目を指定して取得します。
- 現在の作業に必要なスキルと参照資料だけを読みます。同一セッションで内容を把握済みの指示は、変更や文脈の欠落がない限り再読しません。
- 共通指示は一か所にまとめ、他のルールから参照します。更新時は重複する説明や不要な常時適用指示を整理し、無関係な設定には変更を広げません。

## ログと検証

- 長いログはファイルに保存し、終了コードと必要な箇所だけ取得します。成功時は要約、失敗時はエラー周辺や末尾を確認し、不足するときだけ範囲を広げます。秘密情報をログや引き継ぎ記録へ残しません。
- 成功済みの検証は、対象コミット・関連ファイル・実行環境と結果を確認し、結果に影響する変更がない限り繰り返しません。過去の成功を、変更後の検証結果として扱ってはいけません。
- 対象を絞った確認後に、必要なTest・Lint・Build・統合テストをまとめて実行します。失敗、関連変更、未解決の懸念がある場合に再検証します。
- Docker・Gradle・SDKのキャッシュを再利用します。再構築・再取得・高コストな再実行の前に、新たに何を確認できるかを明確にし、同じ結果しか得られない再試行は避けます。

## 報告と再開

- 途中報告は判明事項、次の確認、ブロッカーに絞り、最終報告では変更内容、検証結果、未実施の確認と理由を簡潔に伝えます。長いログを転載しません。
- 引き継ぎはブランチ・コミット、関連Issue/PR、未対応事項、検証コマンド・結果・証拠の場所に絞ります。再開時は現在との差分を確認し、変化がなければ履歴の全取得や成功済み検証を繰り返しません。

## 優先順位

ユーザーの明示指示、正確性、安全性、リポジトリの完了条件を優先します。必要な読み取り・検証・レビュー・承認を省略する理由に、このルールを使ってはいけません。
