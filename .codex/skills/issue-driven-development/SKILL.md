# Issue 起点の開発ルール

## ワークフロー

1. リポジトリを変更する前に [`../../DEVELOPMENT.md`](../../DEVELOPMENT.md) を読みます。
2. 関連 Issue に目的と受入条件が定義されていることを確認します。
3. 影響を受けるドメインを特定し、文書化された依存方向を維持します。
4. 受入条件を満たす最小限の変更を実装します。
5. 必要に応じて、正常系、境界値、代表的な異常系の単体試験を追加します。
6. 秘密情報、権限、外部入力、ログ、依存関係、ストレージへの影響を確認します。
7. TODO を検索し、後続対応が `TODO(#<Issue番号>): <何を、なぜ>` の形式であることを確認します。
8. 利用可能な単体試験、Lint、Build を実行します。実行できない確認とその理由も記録します。
9. 差分が Issue の範囲内であることを確認し、設計、試験、セキュリティ確認、TODO、コマンド結果を報告します。

## アーキテクチャ上の制約

- `domain` を Android Framework、UI、永続化、通信への依存から分離します。
- ユースケースの調整は `application` に配置します。
- Android API、永続化、通信、ファイルアクセスは `infrastructure` に隔離します。
- Compose UI、ViewModel、画面状態、入力処理は `presentation` に配置します。
- 依存方向は `presentation` と `infrastructure` から `application`、さらに `domain` へ向けます。

## 完了条件

- 関連する確認が成功するか、実行環境の制約が文書化されるまで、作業を完了扱いにしません。
- 必須 CI ジョブが失敗している変更はマージしません。
- Pull Request は一つの Issue に集中させます。
