# 開発ルール

guri-launcher の変更は GitHub Issue を起点とし、目的と受入条件を確認して進めます。調査と検証には [トークン効率ルール](skills/token-efficient-development/SKILL.md) を適用します。

## 開発の進め方

1. 対応する Issue を確認します。該当するものがなければ作成し、背景・目的・受入条件を記載します。
2. 作業ブランチで、影響する責務と依存関係を確認し、目的を満たす範囲で実装・検証します。
3. 差分に関係するセキュリティと TODO を確認し、結果を PR に記載します。
4. レビュー指摘に対応し、必須 CI の成功とレビュー完了を確認してから `main` へマージします。
5. 受入条件を満たした Issue をクローズします。未確認事項があれば明記します。

設計や PR の説明量は変更の規模に合わせます。文書だけの修正や単純な変更に、新しい設計書や抽象化を一律に求めません。

## 責務と依存方向

DDD の考え方を使って、ドメインのルールを UI や OS の都合から分離します。レイヤは責務の境界です。定数表示や単純な委譲のためだけにクラス・ユースケース・DI コンテナを作る必要はありません。

| レイヤ | 責務 |
| --- | --- |
| domain | ビジネスルールと状態遷移。Flutter、Android Framework、永続化、通信に依存させません。 |
| application | ユースケースの処理を調整します。外部機能が必要なら抽象を介し、Android API を直接呼びません。 |
| infrastructure | Android API、MethodChannel、永続化、通信などの外部依存を実装します。 |
| presentation | Flutter の画面、画面状態、入力、UI のライフサイクルを扱います。ドメインルールを重複させません。 |

依存は `presentation` / `infrastructure` から `application`、さらに `domain` へ向けます。不要なレイヤや中継処理は追加しません。

## コード・テスト・記録の書き分け

- **コードには How**：どう実現するかを、処理と命名で表します。
- **テストコードには What**：何を保証するかを、前提・操作・期待結果で表します。実装の構造をなぞるだけのテストは避けます。
- **コミットログには Why**：なぜ変更が必要かを記します。件名で変更の目的を伝え、必要なら本文に背景や判断理由を補います。
- **コードコメントには Why not**：別の自然な方法を採用しない理由や、変更時に見落としやすい制約を記します。コードを読めば分かる処理の説明は重ねません。

すべてのコードにコメントを付ける必要はありません。判断の理由が読み取れない箇所に絞り、コードの変更時にコメントも見直します。公開 API の利用方法など、利用者に必要な説明はドキュメントコメントに記載します。

## 試験と検証

- 振る舞いの変更には単体試験を追加・更新し、正常系と、変更に関係する境界値・異常系を検証します。文書や整形だけの変更に、新しい単体試験は不要です。
- domain と application は Android Framework に依存しないローカルテストで検証します。Flutter の画面・ライフサイクルは必要に応じて Widget テストで確認します。
- 不具合修正では、可能な限り修正前に再現テストを追加します。
- 外部依存のために試験が不安定になる場合はテストダブルを使います。実際の OS 操作は、単体試験とは区別して端末で確認します。
- 実装変更では、利用可能な Test・Lint・Build を実行します。結果に影響する変更がない検証は繰り返さず、未実施の確認と理由を記録します。

Flutter の基本的な確認は次のとおりです。

```shell
make test
make lint
make assemble-debug
```

`make check` は上記に Android・リリース用スクリプト試験を加えて実行します。文書のみの変更はリンクや差分など、変更内容に合った確認を行います。ローカルで実行できない確認は理由と代替確認を PR に記載し、必須 CI が失敗している PR はマージしません。

## セキュリティ

差分が影響する権限、外部入力、ログ、依存関係、ストレージを確認します。

- API キー、トークン、パスワード、署名情報をコミットしません。GitHub Actions Secrets やローカル環境変数で管理します。
- Android の権限は必要最小限にします。
- Intent、URI、ユーザー入力など、外部から受け取る値を使用前に検証します。
- 秘密情報・個人情報をログへ出力せず、保存する情報には適切な保存先とアクセス範囲を設定します。
- 依存関係を追加・更新するときは、必要性、既知脆弱性、保守状況を確認します。
- 未解決のリスクは Issue に記録し、影響に応じて優先度とマージ可否を判断します。

## TODO

後続対応を残す場合は、対応する Issue を作成し、コードに `TODO(#<Issue番号>): <何を、なぜ>` と記載します。Issue には完了条件を記載します。変更範囲の TODO を確認し、解決済みのものと一時的なデバッグコードを削除します。

## ブランチと Pull Request

ブランチ名は `<変更種別>/<Issue番号>-<概要>` とします。変更種別は `feature`、`fix`、`refactor` などを使います。

PR は単一の目的に絞り、次を記載します。定型的な説明を繰り返す必要はありません。

- 関連 Issue。受入条件を満たす場合は `Closes #<Issue番号>`、未完了なら `Refs #<Issue番号>` を使います。
- 変更の目的と結果、レビューに必要な設計判断。
- 試験・Lint・Build の結果と、未確認事項・実行できなかった理由。UI 変更は動作確認結果またはスクリーンショットも記載します。
- 差分に関係するセキュリティ確認、残存 TODO と対応 Issue（なければ「なし」）。

レビュー後の修正は影響する検証を行い、最終差分に対する必須 CI の成功とレビュー完了をマージの条件にします。
