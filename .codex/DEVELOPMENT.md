# 開発ルール

この文書は、guri-launcher の変更を Issue 起点で安全かつ一貫して進めるための標準ルールを定義します。

## 基本方針

- すべての実装は GitHub Issue を起点とし、目的と受入条件を実装前に明確にします。
- リポジトリ作業全体に [トークン効率ルール](skills/token-efficient-development/SKILL.md) を適用します。
- 設計では DDD（Domain-Driven Design）の考え方に従い、対象ドメイン、責務、依存関係を整理します。
- 実装と同時に単体試験を追加し、変更した振る舞いを検証します。
- 秘密情報、権限、入力値、外部依存、ログ出力などのセキュリティリスクを確認します。
- Pull Request（PR）は対応 Issue を紐付け、ローカル確認を終えてから作成します。
- CI が成功し、レビューされた PR だけを `main` へマージします。

## 標準開発フロー

1. Issue を作成する。
2. Issue に背景、目的、対象ユースケース、受入条件を記載する。
3. DDD に基づき、対象ドメイン、各レイヤの責務、依存関係を設計する。
4. 秘密情報、権限、入力値、外部依存、ログ出力などのセキュリティ観点を確認する。
5. 命名規則に従って作業ブランチを作成する。
6. 設計した責務に沿って実装する。
7. 変更した振る舞いに対する単体試験を実装する。
8. 追加または残存する TODO を確認し、必要な後続 Issue を作成する。
9. 単体試験、Lint、Build をローカルで実行する。
10. 対応 Issue と確認結果を記載した PR を作成する。
11. GitHub Actions の CI がすべて成功することを確認する。
12. レビューを受け、指摘に対応する。
13. CI 成功後に PR を `main` へマージする。
14. PR の自動クローズ記法または手動操作で Issue をクローズする。

## DDD に基づく責務分離

初期段階では過剰なモジュール分割を避けつつ、次のレイヤの責務と依存方向を明確にします。

### domain

- ビジネスルール、ドメインモデル、値オブジェクトを表現します。
- Android Framework、UI、永続化、通信などの技術詳細へ直接依存させません。
- 他のレイヤから利用される中心的なルールを保持します。

### application

- ユースケースを実行し、処理の流れを調整します。
- domain のモデルとルールを利用します。
- 外部機能が必要な場合は抽象へ依存し、具体的な Android API や永続化処理を持ちません。

### infrastructure

- Android API、永続化、通信、ファイル操作などの外部依存を実装します。
- domain または application が定義した抽象の実装を提供します。
- 技術詳細を他のレイヤへ漏らさないようにします。

### presentation

- Compose UI、ViewModel、画面状態、ユーザー入力を扱います。
- application のユースケースを呼び出し、ドメインルールを UI 内へ重複実装しません。
- Android 固有の表示・ライフサイクル処理をこのレイヤに閉じ込めます。

依存は原則として `presentation` と `infrastructure` から `application`、さらに `domain` の方向へ向けます。domain は外側のレイヤを知りません。

## 単体試験ルール

- 実装と同時に、変更した正常系、境界値、代表的な異常系の単体試験を追加します。
- domain と application のロジックは、Android Framework に依存しないローカル unit test で検証します。
- 不具合修正では、可能な限り修正前に不具合を再現するテストを追加します。
- テスト名から前提、操作、期待結果が理解できるようにします。
- 外部依存はテストダブルに置き換え、テストを決定的かつ独立して実行できるようにします。
- PR 作成前に全単体試験を実行し、成功結果を PR 本文へ記載します。

## セキュリティルール

実装時とレビュー時に、少なくとも次の項目を確認します。

- API キー、トークン、パスワード、署名情報などの秘密情報をコミットしません。GitHub Actions Secrets やローカル環境変数で管理します。
- Android の権限は必要最小限とし、不要な権限を Manifest に追加しません。
- Intent、URI、ユーザー入力、外部アプリから受け取る値を検証し、無条件に信頼しません。
- 秘密情報、個人情報、認証情報をログへ出力しません。
- 外部ライブラリは必要性、既知脆弱性、保守状況を確認してから追加します。
- ファイルや設定値は適切な保存先とアクセス範囲を選び、他アプリから不要に参照できないようにします。
- セキュリティ上の懸念は通常の TODO として放置せず、優先度の高い Issue として管理します。

## TODO 管理ルール

- コード内 TODO は原則として `TODO(#Issue番号): 何を、なぜ後回しにしたか` の形式にします。
- 後続対応が必要な TODO には GitHub Issue を作成し、コードからその番号を参照します。
- 意図や完了条件が分からない TODO は残しません。
- PR 作成前に追加・残存 TODO を検索し、PR 本文に一覧と対応 Issue を記載します。
- 一時的なデバッグコードと不要になった TODO はマージ前に削除します。
- セキュリティに関係する未対応事項は、通常の TODO として長期間残しません。

例:

```kotlin
// TODO(#18): 本番署名へ切り替える。初期リリースでは debug signing を使用するため。
```

## ブランチ命名規則

ブランチ名には、変更種別、Issue 番号、短い概要を含めます。

- 機能追加: `feature/{issue番号}-{概要}`
- 不具合修正: `fix/{issue番号}-{概要}`
- リファクタリング: `refactor/{issue番号}-{概要}`

例: `feature/12-corner-swipe`

## Pull Request ルール

PR 本文には最低限、次の内容を記載します。

- `Closes #<issue番号>` などの対応 Issue を自動クローズする記述
- 変更内容
- DDD 上の設計判断と責務分離
- 追加・更新した単体試験
- セキュリティ上の確認事項
- 残存 TODO と対応する Issue（存在しない場合は「なし」）
- 実行した単体試験、Lint、Build のコマンドと結果
- UI 変更時のスクリーンショットまたは動作確認結果
- レビュー時に重点的に確認してほしい点

PR は小さく、単一の目的に絞ります。レビュー指摘による修正後もローカル確認と CI を再実行します。

## ローカル確認と CI

Android プロジェクト導入後は、PR 作成前に原則として次のコマンドを実行します。

```shell
make test
make lint
make assemble-debug
```

プロジェクト構成によりコマンドが利用できない場合は、その理由と代替確認を PR 本文に記載します。ローカル確認は CI の代替ではなく、CI はマージ前の最終ゲートです。いずれかの必須ジョブが失敗している PR は `main` へマージしません。

## Definition of Done

変更は、次の条件をすべて満たしたときに完了とします。

- [ ] Issue に目的と受入条件が定義されている
- [ ] DDD の責務と依存方向に沿って設計・実装されている
- [ ] 変更した振る舞いの単体試験が追加され、成功している
- [ ] セキュリティ観点を確認している
- [ ] TODO を整理し、後続対応に Issue が紐付いている
- [ ] Lint と Build を含むローカル確認が成功している
- [ ] PR に対応 Issue、設計判断、試験、確認結果が記載されている
- [ ] CI の必須ジョブがすべて成功している
- [ ] レビューが完了している
